# خطة اختبار الوظائف التي تكتب بيانات — بيئة معزولة تمامًا

نسخة Preview الحالية للقراءة فقط (كل عمليات الكتابة تُرفض بـ 403، والإدارة مغلقة، وFirebase معطّل). الوظائف التالية تحتاج كتابة، لذلك تُختبر في بيئة منفصلة لا تملك أي صلاحية على بيانات الموقع المباشر. كل الأدوات مجانية.

## القاعدة الذهبية

- لا يُستخدم أي سر من أسرار الموقع المباشر (GitHub token، Airtable، Paymob، Bosta، D1 الإنتاجي، Firebase الإنتاجي).
- لا يُكتب أي شيء في فرع `products-data` أو `main` أو قاعدة Firebase/Airtable الحقيقية.
- بيئة الاختبار لا تُفهرس (`noindex` + `robots: Disallow`) ولا تُنشر على `popekyrillos.store`.
- لا يتم `git push` لأي فرع اختبار (أي push يشغّل Workers Builds على Worker الإنتاج).

## الخيار الموصى به: معمل اختبار محلي على جهازك

| المكوّن | بديل الاختبار | لماذا هو معزول |
|---|---|---|
| Cloudflare Worker | `wrangler dev --local` على `127.0.0.1` | يعمل على جهازك فقط |
| D1 (حدود الطلبات والتحليلات) | D1 محلي (`--persist-to`) | ملف على جهازك |
| Firebase Auth + Firestore | Firebase Emulator Suite (مشروع `demo-popekyrillos`) | الكود يتصل بالمحاكي فقط على localhost وعند وجود `emulator` في إعداد محلي؛ إعداد الإنتاج لا يحتويه |
| GitHub (نشر المنتجات والأقسام والصور) | مستودع GitHub **خاص جديد للاختبار** + Fine-grained token مقصور على هذا المستودع وحده | التوكن لا يرى مستودع المتجر أصلًا |
| Airtable (الطلبات) | Base تجريبية فارغة بنفس الأعمدة + توكن مقصور عليها، أو بدون Airtable (الطلب يفشل بأمان) | لا وصول للـ Base الحقيقية |
| Paymob / Bosta | بدون مفاتيح (طرق الدفع اليدوية: كاش / إنستاباي) — أو مفاتيح Paymob التجريبية | لا يتم تحصيل أو شحن حقيقي |

### المطلوب منك (مرة واحدة)

1. إنشاء مستودع خاص على GitHub باسم مثل `popekyrillos-staging-data` ونسخ `products.json` و`category-taxonomy.js` الحاليين إليه في فرع `products-data`.
2. إنشاء **Fine-grained personal access token** بصلاحية `Contents: Read and write` على هذا المستودع **فقط**، وحفظه في ملف `.dev.vars` محلي (مستبعد من git) — لا ترسله في المحادثة.
3. (اختياري للطلبات) نسخ هيكل Base الطلبات في Airtable إلى Base تجريبية بدون بيانات، وتوكن مقصور عليها.
4. اختيار كلمة مرور تجريبية للوحة الإدارة المحلية في `.dev.vars`.

أنا أجهّز: ملف `wrangler.staging-local.toml` (بدون routes ولا D1 إنتاجي)، إعداد Firebase محلي يشير للمحاكي، وأوامر التشغيل، ثم أتحقق قبل أي اختبار أن كل الأسرار المستخدمة ليست أسرار الإنتاج.

## حالات الاختبار

### 1) تسجيل الدخول بـ Google
- فتح نافذة الدخول → يظهر حساب Google وهمي من المحاكي → الدخول.
- المتوقع: اسم العميل في الهيدر، وزر الحساب يعمل، ولا طلب يخرج إلى `googleapis.com` الحقيقي (يُتحقق من تبويب الشبكة).

### 2) الجلسة بعد Refresh
- بعد الدخول: Refresh عادي، ثم Ctrl+F5، ثم فتح تبويب ثانٍ، ثم إغلاق المتصفح وفتحه.
- المتوقع: الجلسة باقية، حالة "جارٍ التحقق…" تظهر لحظيًا ثم الاسم، عداد السلة صحيح.
- تسجيل الخروج من تبويب → التبويب الآخر يخرج أيضًا.

### 3) السلة للزائر وللعميل المسجّل
- زائر: إضافة منتج له اختيارات (مثل البخور 250 جرام) ومنتج بدون اختيارات ومنتج ميدالية (خشب زان).
- الدخول: سلة الزائر تُدمج في سلة الحساب بلا تكرار.
- تعديل الكمية والحذف في تبويبين.
- المتوقع: الأسعار = أسعار البيانات المنظمة (215/425… و18/27)، ولا يظهر "غير متاح" لاختيار متاح.

### 4) حفظ بيانات SEO من الإدارة
- فتح منتج ← قسم "محركات البحث (SEO)" ← كتابة عنوان ووصف وAlt ← حفظ ونشر.
- المتوقع: commit في **مستودع الاختبار فقط**، وصفحة المنتج المحلية تعرض العنوان والوصف والـ Alt الجديدة خلال دقيقة، وبقية المنتجات بلا تغيير (مقارنة الملف قبل/بعد).
- مسح الحقول ← الحفظ ← العودة للقيم التلقائية.

### 5) نشر المنتجات وتعديلها
- إضافة منتج جديد بسعر وصورة ← نشر ← يظهر في `/sitemap.xml` المحلي وفي صفحة قسمه.
- تعديل سعر اختيار ← نشر ← يتغير السعر في الصفحة والبيانات المنظمة والسلة.
- جعل منتج "غير متاح حاليا" ← يبقى في الـ sitemap مع `OutOfStock`.
- حذف منتج ← صفحته 404 ويختفي من الـ sitemap.

### 6) تحديث صور الأقسام
- رفع صورة قسم فرعي جديدة ← نشر الأقسام.
- المتوقع: الصورة تُرفع إلى مستودع الاختبار، وتظهر في الصفحة الرئيسية والقسم، وكل المنتجات والأقسام الأخرى سليمة (نفس اختبار `category-image-publish` الذي نجح على نسخة البيانات الحقيقية للقراءة فقط).

### 7) إتمام الطلب
- إتمام طلب بطريقة "كاش" ثم "إنستاباي".
- المتوقع: السعر يُحسب من الكتالوج على الخادم (لا يمكن تعديله من المتصفح)، رقم تتبع يظهر، صفحة تتبع الطلب تعمل، حد الطلبات (5 لكل رقم/ساعة) يعمل على D1 المحلي، والطلب يُسجَّل في Airtable التجريبية فقط (أو يفشل برسالة واضحة إن لم تُجهّز).

## معايير النجاح قبل طلب النشر

- كل الحالات السابقة ناجحة في المعمل المحلي.
- مقارنة سجل الشبكة: لا طلبات إلى `api.github.com/repos/<مستودع المتجر>` ولا إلى Airtable/Firebase الإنتاجيين.
- الموقع المباشر لم يتغير (رقم الإصدار والأسرار كما هي).
